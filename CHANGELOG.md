# Changelog

## [2026-09-05] - Phase 9 verification fixes
**What changed:** Hardened the Phase 9 snapshot rebuild path after a code review of the Go Relay handlers. Closed five issues:
- **Data race:** `HandleSnapshotBegin` now consults a mutex-guarded helper (`hasActiveSessionForAccount`) instead of iterating the shared `rebuildSessions` map bare, so the single-flight check no longer races concurrent session mutations (`handler/snapshot.go`).
- **Abort → failed status:** `abortRebuildSession` now flips an in-flight (`delivered`) `rebuild_requests` row to `failed` (single-flight guarantees at most one per node), so operators can see a rebuild outcome instead of a permanent `delivered` (`handler/snapshot.go`).
- **Reason validation:** `POST /rebuild` rejects reasons outside the protocol enum (`admin | restore | schema_mismatch`) with `400` instead of storing/forwarding junk; validation extracted into a pure `validateRebuildReason` and unit-tested (`handler/rebuild.go`, `rebuild_test.go`).
- **Retention:** added `handler/rebuild_prune.go` (`pruneExpiredRebuildRequests`) — hourly sweep deletes `delivered`/`failed` `rebuild_requests` older than 30 days, wired in `main.go` next to the tombstone pruner; pending rows are never pruned.
- **Test integrity:** the out-of-order-chunk integration test now sends a *signed* BEGIN so the session actually opens and the ordering abort path is genuinely exercised (previously it passed because the unsignd BEGIN was rejected before the session existed). Added integration coverage for failed-status marking and prune behavior.
**Why:** Verification found a `-race`-detectable map race, a test that passed for the wrong reason, and three operational gaps (unbounded `rebuild_requests`, invisible failures, unvalidated input) that would have caused confusing behavior in production.
**Impact:** All `services/relay` handlers are race-clean (`go test -race` green), the request table is bounded at 30 days, aborts are observable, and the integration suite now covers the failure paths it claimed to.
**Follow-ups:** The pending/delivered/failed lifecycle is heuristic (most recent `delivered` row per node); replace with an explicit request↔snapshot correlation ID if multi-snapshot-per-node retries ever need per-request attribution.

## [2026-09-05] - Phase 9: Full Snapshot / Relay Rebuild
**What changed:** Implemented the Phase 9 full-snapshot rebuild path across all three stacks.
- **Protocol** (`packages/protocol`): rewrote `src/messages/snapshot.ts` with typed, homogeneous chunks (`SNAPSHOT_CHUNK_MAX_RECORDS=1000`, `record_type` `file_version|tombstone`), `SnapshotBeginPayloadSchema` carrying `snapshot_sequence` + full `{origin_id → origin_sequence}` cursor map, and `SnapshotEndPayloadSchema`. Added `src/messages/rebuild.ts` (`REBUILD_REQUIRED` with `node_id`/`reason`); wired it into the envelope dispatch; regenerated all 24 JSON schemas; updated tests.
- **Relay schema / routing**: migration `002_snapshot_rebuild.sql` adds `storage_nodes.is_primary` (auto-set `true` on an account's first node), a durable `rebuild_requests` queue, and account-scoped staging `rebuild_files`/`rebuild_file_versions`/`rebuild_tombstones`. `RegisterNode` sets primary-on-first-insert. New `POST /rebuild` trigger endpoint routes `REBUILD_REQUIRED` to the account's online primary, else queues it (delivered on reconnect). Added an hourly tombstone prune (90 days per ADR-0005).
- **Rust node**: new `src/sync/snapshot.rs` builds a snapshot with a monotonic `snapshot_sequence`, full cursor map, BLAKE3 content hash, and typed homogeneous chunks; `client.rs` streams BEGIN/CHUNK/END and handles `rebuild_required`.
- **Go Relay ingestion**: `handler/snapshot.go` implements BEGIN (schema major-compat, Ed25519 signature, primary-role, single-flight-per-account) / CHUNK (strict ordered indexing, staging, raw-record accumulation) / END (signature + recomputed BLAKE3 `content_hash` match, then atomic promotion). `handler/promote.go` drops the §22 cascade FKs, does a per-account DELETE+INSERT replace, restores explicitly-named FKs, resets `sync_cursors` to the snapshot checkpoint (leaving durable `sync_events` intact), and prunes orphaned buffer/envelope rows without touching on-disk buffer files. Aborts clear staged data entirely. Added `github.com/zeebo/blake3`; cross-language hash vector; DB-free unit tests + Postgres integration tests (promotion/§22, happy-path, hash-mismatch abort, out-of-order abort).
**Why:** Phase 9 of the implementation plan — let the Relay fully rebuild its projection from a Storage Node's snapshot after a wipe or schema mismatch, with verifiable integrity and without violating the §22 "buffer entry not in snapshot ≠ delete" rule.
**Impact:** Relay can now recover from full data loss; `REBUILD_REQUIRED`/`snapshot_*` messages added to the wire contract; `is_primary` and `rebuild_*` schema; Rust build/stream; Go ingestion + atomic promotion.
**Follow-ups:** Break the snapshot flow into the Rust `stream_snapshot` ↔ Go `HandleSnapshot*` wiring behind live websockets (tests currently call handlers directly); make public-key/signature handling shared via the scheme constants; add a wire-level e2e that drives the Rust node's real `stream_snapshot` against the Relay.

Added unit tests for auth, config, buffer, and hub logic.
**Why:** Phase 7 of the implementation plan — the Relay handles device/node authentication, coordinates WebRTC signaling (to be added), acts as the central control plane, and provides transient buffer storage for offline storage nodes.
**Impact:** `services/relay` now contains a fully functional HTTP API and WebSocket gateway, communicating with PostgreSQL 17 and Redis 7 (configured via `docker-compose.yml`).

## [2026-09-03] - Storage Node: Configurable Backup Directory
**What changed:** Introduced a run-time configurable data directory for the Rust Storage Node. Added `src/config/` with `mod.rs` (first-run detection, `--data-dir`/`NODUS_DATA_DIR` precedence, `~/.nodus/config.toml` read/write), `prompt.rs` (dialoguer interactive first-run flow with `~/NodusBackup` default and create-if-missing), and `validation.rs` (writable-path probe, cloud-sync folder detection, removable/network mount detection, prior-install marker check). Documented the fixed/user-chosen split in `nodus_implementation_plan.md` §11 and the first-run flow in new §11a; updated the object-store path to `<data_dir>/objects/<prefix>/`; added Phase 5a to `Todo.md`. All relative to the existing docs-only design (the `identity` subdir is reserved for the later node-keypair task).
**Why:** Phase 5a — the node should prompt for a local data directory on first run instead of hardcoding `~/.nodus/objects/`, with unattended-install support so daemon restarts never block, and safeguards against adopting a prior install or a cloud/removable location.
**Impact:** New `src/config/` module and `src/main.rs` boot wiring in `services/storage-node`. New CLI `--data-dir` flag and `NODUS_DATA_DIR` env var. `node.db` is now `<data_dir>/nodus.db`; objects live under `<data_dir>/objects/<prefix>/`. Adds four dependencies to the storage-node crate.
**Follow-ups:** v1 scope boundary — changing `data_dir` after setup is out of scope and needs a migrate-and-verify flow, not a config edit (TODO noted in `docs/architecture`-adjacent plan §11a). Identity subdir task (Phase 5) will populate `~/.nodus/identity/`.

## [2026-09-02] - Phase 4: Protocol Package (`packages/protocol`)
**What changed:** Created the `@repo/protocol` package (packages/protocol) defining the canonical Nodus wire protocol: `src/envelope.ts` (base envelope + `parseMessage` dispatch), `src/version.ts` (schema version constants + compatibility helpers), `src/errors.ts` (generic error envelope, error codes, `ProtocolError`), and per-category message schemas in `src/messages/{control,webrtc,transfer,sync,snapshot}.ts`. Finalized the sync event schema and ordering fields (`src/events/event-types.ts`) with an `EventType` enum and per-type payload validation. Added protocol-local branded types with mapping helpers (`src/types.ts`) so the package is zero-dependency on `@repo/core`. Added a JSON Schema generator (`src/schema-gen.ts`, `pnpm generate:schemas`) emitting `schemas/*.schema.json` for Rust/Go reference. Added 35 vitest round-trip/rejection tests in `tests/`. Wrote `docs/protocol/schema-versioning.md`, `message-catalog.md`, and `event-types.md`, and updated `docs/protocol/README.md` and `Todo.md`.
**Why:** Phase 4 of the implementation plan — define all protocol message types with runtime (zod) validation rather than TS types alone, document the schema versioning strategy, and resolve the "exact sync event schema" and "event ordering guarantees" open items before Phase 8 consumes them.
**Impact:** New package `packages/protocol` (zod v4 runtime-validation, no dependency on core). Adds `schemas/*.json` generated artifacts and `docs/protocol/` documentation. Unblocks Phases 5+ (Rust node, Go relay, relay-client) which build against this contract.
**Follow-ups:** Rust (`serde`) and Go (`encoding/json`) hand-written equivalents must mirror these schemas per `docs/protocol/schema-versioning.md`; regenerate `schemas/` whenever a schema changes.
