# Changelog

## [2026-09-06] - Fix VerifyPairingSession token consumption + spec TTL alignment

**What changed:** `services/relay/internal/handler/pairing.go` `VerifyPairingSession` now atomically redeems the token: the plain `SELECT` is replaced with `UPDATE pairing_sessions SET consumed_at = NOW() WHERE token = $1 AND status = 'ACTIVE' AND consumed_at IS NULL AND expires_at > NOW() RETURNING account_id, node_id, device_public_key, expires_at`. A matched row returns `valid: true` and is consumed in the same statement (concurrent verifies race on the row lock, so only one caller succeeds); an unknown, already-consumed, or expired token yields no rows and returns `valid: false`. Added `services/relay/internal/handler/pairing_test.go` with integration tests for both `CreatePairingSession` (success, node-not-found, device-not-found) and `VerifyPairingSession` (valid consumes token, replay rejected, expired rejected, unknown rejected). Updated the pairing-token TTL in the specs from 5 to 15 minutes to match the implementation: `docs/security/local-endpoints.md` ("TTL: 15 minutes") and `docs/protocol/local-discovery.md` ("15 min TTL"). Fixed a comment typo ("endpooints" → "endpoints").
**Why:** The verify fallback path never consumed tokens — a token redeemed over `POST /pairing/sessions/verify` stayed `ACTIVE` in the Relay DB and could be replayed until `expires_at`, breaking the single-use invariant in `docs/security/local-endpoints.md` ("the first consumer atomically sets consumed_at"). The spec's 5-minute TTL contradicted the shipped 15-minute `pairingTokenTTL` (already documented in this changelog), so the docs were aligned to the working implementation rather than changing behavior.
**Impact:** The Relay's `/pairing/sessions/verify` is now the source of truth for single-use across the hybrid fast/fallback flow (design decision E); a token verified via the fallback cannot be re-verified. Existing behavior for `CreatePairingSession` and `VerifyNodeURL` is unchanged. Six new integration tests run under `TEST_DATABASE_URL` (skipped when unset), consistent with the existing harness pattern.
**Follow-ups:** Confirm the node's fast-path `account_id = "local_push"` pairing is never verified against the Relay table (it is local-only by design); if offline-pair tokens ever need Relay-side revocation, expose a revoke path — token single-use already covers normal replay.

## [2026-09-05] - Phase 10 audit fixes
**What changed:** Closed the security/correctness findings from the Phase 10 implementation audit across the Relay and Storage Node.
- **Tenant isolation (S1)** (`relay/internal/handler/buffer_upload.go`): the `POST /buffer/upload` file-version-existence check now joins `file_versions` to `files` and enforces `f.account_id` — a client can no longer reference another tenant's `(file_id, version_number)` and pollute its own node with foreign rows. Added `TestBufferUploadRejectsForeignVersion`.
- **Stuck-state recovery (C1, C2)** (`relay/internal/buffer/buffer.go`): new `sweepStuckInTransit` reverts `NODE_RECEIVING`/`NODE_VERIFIED` rows older than a 30-min grace back to `RELAY_BUFFERED` (re-adding them to the Redis pending set) so a node that crashes between fetch and ack is re-notified on reconnect instead of stranding the shard forever. Terminal `NODE_STORED` is never touched. Wired into the existing TTL sweep; covered by `sweep_integration_test.go`.
- **Test seed bug (T1)** (`relay/internal/handler/buffer_integration_test.go`): `setupBufferHarness` no longer overwrites its query args with the same two values for every *seed query — the `accounts` row now gets only `account_id` (previously it silently received `(file_id, account_id)`).
- **Closed-channel panic (R2)** (`relay/internal/handler/ws.go`): `checkAndDeliverPendingShards` now sends via `safeSend`, a recover-guarded helper, since it runs outside the hub lock and the client's `Send` channel can be closed mid-backfill.
- **Fetch-URL hardening (D4)** (`storage-node/src/sync/client.rs`, `Cargo.toml`): `relay_http_fetch_url` derives the HTTP endpoint through the `url` crate instead of string surgery, fixing corruption from query strings (`/ws?token=…`), trailing slashes (`/ws/`), and preserving non-`/ws` base paths. Added the `url = "2"` dependency and edge-case tests.
- **Pending-slot orphan guard** (`storage-node/src/sync/client.rs`, `engine.rs`): `record_shard_metadata` re-checks for the `file_versions` row after staging into `pending_shard_fetches` and immediately drains it (via the now-`pub(crate)` `drain_pending_fetches`) if the version synced mid-flight; the re-check is guarded so it never runs the drain against a missing FK target.
- **Docs (Doc1)**: new `docs/architecture/file-state-machine.md` documents the 7-state `file_locations` lifecycle, transition triggers, recovery/redelivery, and invariants; linked from `docs/architecture/README.md`.
**Why:** Audit verdict on Phase 10 was "solid for v1 but fix S1 and C1/C2 before production load": the upload path had a cross-tenant metadata-pollution vector, and a crashed node could permanently strand a buffered shard in a non-terminal state. The remaining items were test integrity, a process-crash panic window, fragile URL derivation, and a latent pending-row race.
**Impact:** Multi-tenant isolation on the buffer upload path is now enforced at the DB query; shard delivery self-heals after node crashes; relay process no longer panics on a client disconnect during pending backfill; node fetch endpoint is robust to odd relay URL configs; state-machine contract is documented for implementers.
**Follow-ups:** Keep `relay_http_fetch_url` base-path semantics in mind if the Relay ever serves the WS and buffer endpoints from different path prefixes; `checkAndDeliverPendingShards` still loads all `RELAY_BUFFERED` rows (no LIMIT) — pagination remains an open tuning item (P2).

## [2026-09-05] - Phase 10: Buffer-and-Relay Transfer (Path C)
**What changed:** Implemented the offline-node shard delivery path end-to-end against the full file state machine (`CREATED → UPLOADING → RELAY_BUFFERED → NODE_RECEIVING → NODE_VERIFIED → NODE_STORED → RELAY_CLEANUP`), no state collapsing. Clients push encrypted shards to the Relay's temporary buffer when the target Storage Node is offline; the node pulls them asynchronously on reconnect, verifies integrity, commits to its object store, and acks the outcome.
- **Protocol** (`packages/protocol`): `shard_upload`/`shard_ack` now carry `version_number` (disambiguates the exact `file_locations` row); `pending_notify` gains `version_number` + single-use `fetch_token`; `size` re-defined as the encrypted wire payload size, not plaintext. Field tables updated in `docs/protocol/message-catalog.md`.
- **Relay schema** (migrations `003`/`004`): `file_locations` gains `hash`/`size_bytes`/`source_device` (needed for `pending_notify` metadata) and a `(node_id, status)` delivery-scan index.
- **Relay HTTP** (`handler/buffer_upload.go`, `handler/buffer_fetch.go`): `POST /buffer/upload` (JWT-authed, X-Nodus metadata headers, BLAKE3 + size verification, upsert-to-`UPLOADING` reservation, FK checks for target-node ownership and version existence, `http.MaxBytesReader` 10 MB cap) and `GET /buffer/fetch` (no JWT — single-use token via Redis `GETDEL`, 10-min TTL; serves bytes, transitions `RELAY_BUFFERED → NODE_RECEIVING`, single-fetch 409 guard).
- **Relay WS/state machine** (`handler/ws.go`, `handler/buffer_notify.go`): `pending_notify` built from row metadata with a fresh fetch token; proactive delivery when the node is online at upload time, reconnect-time delivery via `checkAndDeliverPendingShards` (token re-issued per reconnect since tokens expire while nodes are offline); `shard_ack` `verified` routes `NODE_RECEIVING → NODE_VERIFIED → NODE_STORED` and deletes the buffer copy; `failed` reverts to `RELAY_BUFFERED` for redelivery on next reconnect.
- **Relay sweeper** (`buffer/buffer.go`): TTL sweep now also reaps abandoned `UPLOADING` rows (>1 h grace) to `RELAY_CLEANUP`, keeping the terminal-state invariant; existing `RELAY_BUFFERED` TTL path unchanged.
- **Rust node** (`src/sync/client.rs`, `src/sync/engine.rs`): node sends a `register` envelope after auth (the Relay keys pending delivery on it), handles `pending_notify` → HTTP `GET /buffer/fetch` → BLAKE3-of-body matches `notify.hash`, writes via content-addressed `ObjectStore::put` (object_id must equal the digest), records into `shards` directly or `pending_shard_fetches` when the `file_versions` row hasn't synced yet, then acks `verified`/`failed`. `engine.rs` drains pending fetches into `shards` when `FILE_VERSION_ADDED` lands. Added `reqwest` (HTTP client) and migration `20260905000002_pending_shard_fetches.sql`.
- **Tests:** Relay Postgres integration tests (upload→fetch E2E with single-use token replay rejection, unknown-version/foreign-node/bad-hash rejections, proactive `pending_notify` to an online hub node); Rust unit tests (`relay_http_fetch_url` derivation, pending-fetch drain on version-added, metadata recording direct-vs-pending fallback); updated protocol vitest fixtures for the new required fields.
**Why:** Phase 10 of the implementation plan — the last leg of offline upload: a client must be able to finish syncing while its storage node is powered down, with the Relay holding shards temporarily and the node self-healing on reconnect. Explicit state transitions make multi-node delivery races (double-fetch, stale acks) observable rather than silent.
**Impact:** Full Path C transfer works across the three stacks; offline nodes recover pending shards automatically; the `file_locations` status column is now the single source of truth for the whole 7-state machine; single-use fetch tokens bound replay exposure to a 10-minute window.
**Follow-ups:** Wire-level e2e driving the real Rust `run_sync_session` against the Relay (handlers are currently tested directly); decrypt-and-verify on the client once decryption lands; backoff on node reconnect; sweep notification for `RELAY_CLEANUP` rows so clients can surface abandoned shards.

## [2026-09-05] - Phase 9 verification fixes
**What changed:** Hardened the Phase 9 snapshot rebuild path after a code review of the Go Relay handlers. Closed five issues:
- **Data race:** `HandleSnapshotBegin` now consults a mutex-guarded helper (`hasActiveSessionForAccount`) instead of iterating the shared `rebuildSessions` map bare, so the single-flight check no longer races concurrent session mutations (`handler/snapshot.go`).
- **Abort → failed status:** `abortRebuildSession` now flips an in-flight (`delivered`) `rebuild_requests` row to `failed` (single-flight guarantees at most one per node), so operators can see a rebuild outcome instead of a permanent `delivered` (`handler/snapshot.go`).
- **Reason validation:** `POST /rebuild` rejects reasons outside the protocol enum (`admin | restore | schema_mismatch`) with `400` instead of storing/forwarding junk; validation extracted into a pure `validateRebuildReason` and unit-tested (`handler/rebuild.go`, `rebuild_test.go`).
- **Retention:** added `handler/rebuild_prune.go` (`pruneExpiredRebuildRequests`) — hourly sweep deletes `delivered`/`failed` `rebuild_requests` older than 30 days, wired in `main.go` next to the tombstone pruner; pending rows are never pruned.
- **Test integrity:** the out-of-order-chunk integration test now sends a *signed* BEGIN so the session actually opens and the ordering abort path is genuinely exercised (previously it passed because the unsignd BEGIN was rejected before the session existed). Added integration coverage for failed-status marking and prune behavior.
**Why:** Verification found a `-race`-detectable map race, a test that passed for the wrong reason, and three operational gaps (unbounded `rebuild_requests`, invisible failures, unvalidated input) that would have caused confusing behavior in production.
**Impact:** All `services/relay` handlers are race-clean (`go test -race` green), the request table is bounded at 30 days, aborts are observable, and the integration suite now covers the failure paths it claimed to.
**Follow-ups:** The pending/delivered/failed lifecycle is heuristic (most recent `delivered` row per node); replace with an explicit request↔snapshot correlation ID if multi-snapshot-per-node retries ever need per-request attribution.
