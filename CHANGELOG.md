**Why:** spec (Todo.md Phase 7a §4) requires the pairing screen to sit on the same session-cookie boundary as the rest of the client — the browser must never hold a Relay token — and the old flow was broken against the §1/§2 token-free API.

## [2026-09-07] - Transfer Manager: repair data-return path (P2) + object_id threading (P3)

**What changed:** Finished the §21a repair receive path behind the Option B backhaul (mDNS + authenticated HTTP). P3: `object_id` (the BLAKE3 content hash) is now threaded end-to-end — `ShardTransferRequest`/`TransferResult` gained `object_id: String`, `fetch_shard(peer, object_id)` takes it directly, and `DegradedShard` was slimmed to `object_id` (its `file_id`/`version_number`/`shard_index` were unread once fetch became object-addressed; the `find_degraded_shards` query selects `DISTINCT s.object_id`). P2: `TransferResult` gained `data: Vec<u8>`, and the dead `TODO(receive-path)` in `reconcile.rs` `run_repairs` is replaced by a real restore: on success it BLAKE3-verifies the fetched bytes against `object_id`, atomically writes them (`<data_dir>/objects/<ab>/<object_id>` via same-directory temp-file + rename), then flips `storage_objects` `DEGRADED → STORED`.
- **Receive endpoint** (`src/local/server.rs`): new `GET /nodus/shard/{object_id}` with stateless node auth — the requester signs `"{node_id}:{object_id}:{timestamp_ms}"` and sends it in `X-Nodus-Node-Id`/`X-Nodus-Timestamp`/`X-Nodus-Signature` headers; the receiver looks the caller up in `trusted_nodes`, enforces a ±60 s freshness window, and maps failures to `401 UNAUTHORIZED` (unknown/stale/bad signature) or `404 NOT_FOUND`. The previously-`#[allow(dead_code)]` `store` in `LocalState` is now used.
- **Peer discovery + Path A** (`src/local/mdns.rs`, `src/transfer/node_attempter.rs`): added an mDNS *browser* (`mdns = "3"`, pure-Rust; libmdns advertises only) with `discover_node(node_id)` matching the responder's `node_id=…` TXT record; `NodePathAttempter` carries a `reqwest::Client` and its `LocalSignaling` arm now does discover → sign → `GET /nodus/shard/{object_id}` → populate `data`, instead of the hard-failure stub. Paths B/C/D remain honest failures for node→node repair.
- **TS parity** (`packages/transfer-manager/src/types.ts`): `TransferResult` gained optional `data?: Uint8Array` and `objectId?: string`.
- **Spec** (`docs/architecture/transfer-manager-spec.md`): rewrote the Re-fetch-from-peer section for the v1 behavior (single best-peer fetch, verify + atomic restore + STORED) and documented the node→node Path A HTTP transport + header contract.

**Why:** P2 and P3 were the two blockers for a working repair-receive path: `TransferResult` had no way to carry received bytes, and `fetch_shard` took file/version/shard coordinates while the restore loop needed the content hash it fetches and writes under.

**Impact:** A DEGRADED shard can now be repaired end-to-end when a peer holds a copy and both nodes advertise on the same LAN: mDNS discovery → signed HTTP fetch → hash-verified atomic restore → `STORED`. Because the receiver only serves `trusted_nodes` callers and the requester only writes bytes that hash to the requested `object_id`, a malicious/compromised peer cannot plant arbitrary content. **Follow-ups:** Path B (Relay signaling), Path C (buffer), and Path D still fail honestly for node→node repair — wiring those receive directions is the remaining Phase 13 work. Also note: `trusted_nodes` currently has **no production write path** (every INSERT is in a `cfg(test)` module, and the path cache only UPDATEs), so a node starts with an empty peer set and `trusted_peers_for_repair` finds no one until a seed producer lands — e.g. recording peers encountered during client-initiated transfers, or registering known nodes at pairing/setup.

## [2026-09-07] - Transfer Manager: submit_repairs fan-out fix, graceful semaphore, comment cleanup

**What changed:** `submit_repairs` in `reconcile.rs` now submits one `fetch_shard` per DEGRADED shard to the best-candidate peer (first entry in the ordered `peers` vec) instead of fanning out to all `N×M` peers simultaneously — the executor has no peer-fallback loop, so multiple concurrent fetches of the same shard merely burn pool slots. **Why:** The `N×M` fan-out wasted bandwidth and could starve the 4-slot pool on duplicative requests for the same shard. The semaphore panic risked a crash during graceful shutdown. The original "Populated by the attempter" comment was inaccurate for fetches.

**Impact:** No behavior change to working paths (node→node receive is still unimplemented); repairs now request only 1 fetch per shard per scan, making the pool usage linear in degraded-shard count and eliminating unnecessary peer traffic. `pool.rs` shutdown path is panic-free. ## [2026-09-07] - Phase 13: Transfer Manager

**What changed:** Delivered the Transfer Manager — a bidirectional, per-shard transfer orchestrator with a 4-path fallback chain (Local signaling → Relay signaling → Buffer-and-Relay → Local queue), a persisted path cache, a bounded concurrency pool (default 4), and exponential backoff with jitter — on both the TS client and the Rust Storage Node, wired into the §21a re-fetch-from-peer repair action.
- **Spec** (`docs/architecture/transfer-manager-spec.md`): shared TS/Rust contract — `TransferPath` (4 values, byte-identical string names), `TransferState`, failure taxonomy (transient/permanent, cached-path failure evicts without retry), timeout table (local discovery 2000ms, WebRTC negotiation 4000ms, relay signaling 3000ms), backoff `base*2^attempt + [0, jitter)` (base 500ms / jitter 300ms / max 2 retries per stage), concurrency, path-cache persistence, and the generic Path D `LocalQueue` interface (memory implementation for v1). Decisions locked: fresh mDNS each time (never cache peer IPs), §21 peer selection is brute-force try-all trusted nodes ordered by path-cache hit then recency (no `peer_shard_locations` index).
